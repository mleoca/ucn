# UCN trust contract

Use this reference when an agent, CI job, or script will make decisions from UCN output.

## Evidence classes

`confirmed` means UCN found positive identity evidence such as an exact binding, a target on the same class definition (a same-name class in another module does not count), a validated receiver type, or an owned import/export chain. It does not mean the edge has a calibrated probability.

`unverified` means a syntactic candidate could reach the target but identity could not be established. Each carries the engine reason (`possible-dispatch`, `single-owner`, `method-ambiguous`, `overload-ambiguous`, `configuration-alternative`, ...; the per-language meanings are in [resolution-rules.md](resolution-rules.md)). Preserve and expose these edges. Do not silently treat them as negatives.

`excluded` means the engine found evidence for a different definition, an incompatible receiver, an external package, an unrelated runtime-language boundary, an arity mismatch, or another stated reason. Excluded sites are counted in `ACCOUNT` as other-target lines and exposed with their reasons under `account.excluded` in JSON. Inspect them when investigating an accuracy issue.

`non-call` means the literal name occurred as a definition, import, type reference, property, comment/string, or other text. Use `usages` for the underlying sites; comment/string occurrences appear under `OTHER TEXT` unless `--code-only` (`code_only=true`).

`beyond-text` means semantic binding or alias evidence produced an edge that a literal-name ground set could not observe (Rust `use m::f as g; g()`, a call generated by a macro expansion). A reflective access whose member name is built at runtime from literal fragments (`getattr(self, "_get_%s_perms" % src)`) is also beyond text: it is listed as an unverified caller with reason `reflection-pattern` and the pattern, never confirmed. A Java single-element annotation (`@Marker("x")`) sets the element `value` without naming it: it is listed as an unverified caller of that element with reason `annotation-shorthand`, and `plan` names the element there when the annotation type resolves.

## Trust lines

Caller, callee and trace views carry the applicable trust lines below, preserved through truncation. Source, definition and test-reference lists do not supply a caller account; request `show` or `impact` when one is needed.

- `ACCOUNT` partitions every line where the name occurs: confirmed, unverified, non-call (import, definition, reference, other text), other-target, unanalyzed (a line in source UCN reads without analyzing), unaccounted.
- `CONTRACT` is the state of that partition: `text-complete` (every literal-name line of project source was classified), `text-complete, zero observed; not deletion proof`, `text-complete over indexed source; N lines in unanalyzed source` (the name also occurs in a bundle, a path excluded in `.ucn.json`, an oversized file or an unsupported language, listed in the WARNING), or `degraded; see WARNING`. No state is semantic completeness: aliases, indirect calls, generated code and runtime dispatch may exist.
- `WARNING` identifies what weakens the claim for this name: unparsed files that contain it, lines in syntax-error recovery regions, its occurrence sites in unanalyzed source (file:line plus the line text), and paths that could not be searched at all (including `git-listing-failed`), which degrade every account. Unanalyzed source the name does not occur in is not mentioned. `usages` and `tests` carry the same disclosure as a note.
- `FILTERED` means query options hid evidence.
- `CALLEE ACCOUNT` partitions a function's call sites (confirmed, unverified, external/builtin, excluded, filtered); `TREE ACCOUNT` does the same for the interior of a caller-direction `trace`.

## Conservation scope

The caller account partitions a literal-name text-occurrence ground set. A conserved account answers: "Did UCN explain every observed literal-name line?" It does not answer: "Did UCN discover every semantically possible runtime caller?"

Required automation checks:

1. `account.conserved` is true.
2. `account.contract.textComplete` is true.
3. No unreadable or unparsed files are reported, `account.opaque.count` is 0, and no ground line sits in a syntax-error recovery region (`account.recovered`, WARNING line).
4. No contract metadata was lost to truncation.
5. Unverified and excluded reasons are retained for review.

Even when all five hold, `account.contract.semanticComplete` remains false. Use compiler/type-checker, test, runtime, and framework evidence for semantic decisions.

`account.contract.observedTextZero` is safe only for the claim "the complete observed literal-name ground set contained no caller candidates or beyond-text edges." It is explicitly not safe-delete proof.

## Numeric fields

`evidenceScore` (and the `confidence` alias where present) is an ordinal weight used for ordering and thresholding evidence classes. `scoreKind` is `ordinal-evidence-not-probability`. Never display it as measured accuracy or use it as a probability in risk calculations.

## Provenance

Caller and callee JSON carries compact `provenance`: `rule`, contributing `rules` when there is more than one, `validation`, and the receiver's source and origin line when recorded. Incomplete proofs include a `diagnostic`, also shown in text. Callees retain compact `siteProvenance` for each distinct occurrence; their summary uses the weakest confirmed site's rule. Exclusions expose counts by rule and validation under `account.excluded.evidenceSummary`.

A lone project owner of a method name does not identify an untyped receiver. Such candidates stay unverified with `single-owner`; importing the class does not change that. `provenance-incomplete` means the available facts cannot establish this declaration. Inspect the site and diagnostic before editing it. Neither reason is permission to discard a possible caller. `validation: unsupported` means the witness collector does not cover that path (for example a wildcard re-export or an external inherited member); the existing classification is kept in report-only mode and is not a validated proof. Missing or inconsistent facts on a supported lookup still route unverified. A confirmed edge's `validation` is always `establishes-target` or `unsupported`: an edge whose witness proves another declaration, or cannot finish the lookup, is listed unverified (`provenance-incomplete`) instead. Super calls (`super.m()`, `super().m()`, C# `base.M()`) are looked up from the enclosing class's bases. An unverified alias call (`f = obj.m; f()`) can carry `establishes-target`: the target is proven, the call goes through a local alias.

## Release evaluation

Releases are gated on pinned real repositories against independent oracles (ts-morph, Pyright, gopls, rust-analyzer, JDT LS, Roslyn, clangd): 100% in-scope caller, callee and value-reference recall with zero unaccounted oracle edges, at least 98% confirmed-tier precision, full conservation, zero false-dead claims in the default `deadcode` audit, exactly agreeing cross-command claims for the same handle (`find`, `show`, `source`, `impact`, `tests`, `check`, caller `trace`), and bounded unverified review burden (at most 10% of exact true edges left unverified, at least 80% of targets with no actionable ambiguity, at most five actionable candidates at p95).

Performance gates cover throughput, memory and per-class query latency on the reference host. Existing capabilities compare against the previous release. A newly introduced reference band or declaration inventory compares the complete command against its first working revision, with the same 1.15x and +5 ms allowance. The original release comparison stays visible; extra proof work or changed confidence alone does not qualify for a new baseline. Passing these sampled gates is evidence for the measured static evidence classes, not complete runtime knowledge of dynamic dispatch, generated code, reflection or external dependencies.

## Truncation

CLI and MCP text share the same 10K targeted / 3K broad default budgets and 100K ceiling. Room for every trust line (ACCOUNT, CONTRACT, WARNING, FILTERED, CALLEE ACCOUNT, TREE ACCOUNT) is reserved before any body text, and truncation appends the ones the kept body does not show. A limit that cannot hold them withholds the answer: the text states how many trust lines it shows and the budget that carries all of them, and never shows body text without them. MCP results may additionally include:

```json
{
  "truncated": true,
  "contractMetadata": ["ACCOUNT: ...", "CONTRACT: ..."],
  "contractMetadataComplete": true
}
```

When `contractMetadataComplete` is false, narrow the query or increase the output budget. A truncated result without complete contract metadata cannot support an automated breaking-change decision.

## Suggested machine policy

Allow an automated change to proceed to compiler/tests only when:

- the exact target is pinned by handle;
- the account is conserved and text-complete;
- warnings and filtered counts are zero;
- unverified sites are either zero or explicitly reviewed;
- `ucn repo --sections=health --deep` reports no parse failure/recovery and its task-specific readiness has been reviewed;
- the repo health report lists no unsupported source handoff relevant to the change;
- the change is still validated by the language toolchain and relevant tests.

Never auto-delete from a UCN-only signal. Computed dispatch is reported as a health blind spot, and modeled registry members are withheld from candidates, but neither protection proves runtime reachability. C/C++ token-pasting macro invocations and Rust `macro_rules!` invocations that cannot be expanded are reported the same way. Require usages, entry-point review, public API review, and external validation.
